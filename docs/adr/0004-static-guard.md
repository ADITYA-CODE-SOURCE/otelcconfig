# ADR-0004: Static Guard for Undeclared Configuration Access

- **Status:** Accepted
- **Date:** 2026-08-19
- **Deciders:** Project maintainers
- **Related:** [RFC 0001](../rfc/0001-declarative-instrumentation-configuration.md),
  [ADR-0003](0003-bake-at-build-time.md)

## Context

ADR-0003 established that hooks read configuration only through the typed
`runtime` package and never parse YAML. That contract is enforceable by review
alone, which is weak for a mechanism whose entire value is "the binary cannot
misbehave due to configuration". Any hook could bypass the typed API by reading
an option env var directly, parsing YAML, or hand-registering a snapshot.

## Decision

Add a **static analyzer** that rejects undeclared configuration access in hook
packages. It enforces three rules:

1. `runtime.Register` is only callable from generated baked code (files with the
   `// Code generated by otelcconfig. DO NOT EDIT.` header).
2. Option values are never read from the environment: `os.Getenv` /
   `os.LookupEnv` calls whose argument matches a declared option env var
   (`OTEL_GO_ENABLED_INSTRUMENTATIONS`, `OTEL_GO_DISABLED_INSTRUMENTATIONS`) are
   flagged.
3. Hooks never parse YAML: imports of `gopkg.in/yaml.v3` are flagged outside
   tooling packages (`config/`, `cmd/`).

The analyzer is **import- and name-based** (go/parser over a directory): it
resolves calls by import path and selector, with no extra module dependencies.
Reports `path:line:col: message` diagnostics; exit 0 clean, 1 on violations.

### Rules

1. `otelcconfig guard <dir...>` checks whole directories (non-recursive), skipping
   `_test.go` and `_gen.go` files; generated code is exempt via its header.
2. `make guard-check` runs the analyzer over the repository's own hook packages
   (`./demo ./runtime ./baked ./cmd/demo`) as part of `make check` and CI.
3. The rule set is intentionally small: rules that cannot be expressed reliably
   without type information (e.g. stringly-typed path lookups) are deferred
   rather than approximated.

## Consequences

- The runtime contract is mechanically enforced on the repository itself.
- Hook code can only consume configuration through the baked typed API.
- Trade-off: name/import-based analysis can produce false positives when a
  package shares a selector name (e.g. a different package exporting `Register`).
  The current rules match on the exact runtime import path, so this is limited.
  A full go/types pass (golang.org/x/tools) is the documented upgrade path if the
  prototype graduates upstream.

## Alternatives considered

- **golang.org/x/tools/go/analysis** (deferred) — full type information and
  better precision, but adds a large dependency to a deliberately
  dependency-light module.
- **Convention/review only** (rejected) — unenforceable at CI time.
- **Runtime enforcement** (rejected) — panics when hooks violate the contract
  are exactly what baking is meant to prevent.
